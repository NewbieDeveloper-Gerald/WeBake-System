# Render Backend API Setup — Detailed Blueprint Guide

Goal: deploy the WeBake Express API (`backend/`) as a Render Web Service using
the Blueprint file (`render.yaml`). Start to finish: about 20 minutes, most of
it waiting on the first build.

## Before you start (have these ready)

You will be asked for six secrets during setup. Gather them first so you can
paste straight through without pausing the wizard:

| Secret | Where to get it |
|---|---|
| `DATABASE_URL` | Supabase > Project Settings > Database > **pooler** string (port `6543`). Must start with `postgresql://` and contain `pooler.supabase.com:6543`. The direct string (port 5432) also boots but drops connections under Render's free tier — use the pooler. |
| `FRONTEND_URL` | Your Vercel URL, e.g. `https://webake-xxxx.vercel.app`. **If Vercel isn't deployed yet:** type `https://placeholder.local` for now and replace it later (step 7). Any value boots; a wrong value only affects browser CORS, not the API itself. |
| `ADMIN_PASSWORD` | A strong owner password you invent now (12+ characters, unique). Used once by the seed script, then stored only as a bcrypt hash. |
| `BREVO_API_KEY` | Brevo dashboard > SMTP & API > API Keys. Starts with `xkeysib-`. |
| `SUPABASE_URL` | Supabase > Project Settings > API > Project URL (`https://xxx.supabase.co`). |
| `SUPABASE_SERVICE_ROLE_KEY` | Same page, the `service_role` key ( NOT the `anon` key). Server-only. |

You also need the repo on GitHub (see step 1) and the two Supabase storage
buckets created (`payment-proofs` private, `product-images` public).

## Step 1 — Push the repo to GitHub

Render deploys from git, not from your laptop. The repo must look like this:

```
<repo root>/
├── render.yaml        # the Blueprint (this guide's input)
├── backend/           # rootDir points here
│   ├── package.json   # engines 20.x, scripts: migrate, seed, start
│   ├── server.js
│   └── src/...
├── frontend/
└── docs/
```

Critical details Render depends on:

- `render.yaml` must be at the **repo root** (not inside `backend/`).
- `backend/package.json` must have `engines: { "node": "20.x" }` (already set)
  and the scripts `migrate` (`node src/db/migrate.js`) and `start`
  (Render runs `node server.js` via `startCommand`, the `start` script is backup).
- Commit and push to your default branch (usually `main`).

```bash
git add -A
git commit -m "Deploy backend via Render Blueprint"
git push origin main
```

## Step 2 — Create the Blueprint in Render

1. Log in at dashboard.render.com (create the account with GitHub for easiest
   repo access).
2. Click **New > Blueprint**.
3. If prompted, **Connect GitHub** and grant Render access to the repo
   (all repos, or just this one).
4. Select the repo from the list. Render scans it, finds `render.yaml`, and
   shows a preview: one resource, `webake-api` (Web Service, node, free,
   singapore, rootDir `backend`).
5. **Blueprint name:** anything (e.g. `webake`). This is just a label for the
   group — the service keeps its own name `webake-api`.
6. **Branch:** `main` (or your default). Render auto-deploys on every push to
   this branch — you can turn that off later under Settings.
7. Click **Apply** (wording varies: "Create" / "Deploy"). Render now asks for
   the six secrets from the table above.

## Step 3 — Fill the six secrets

Paste each value carefully — a trailing space in `DATABASE_URL` is the most
common first-deploy failure. Notes per field:

- `DATABASE_URL`: the full pooler string, exactly as Supabase shows it
  (password included). No quotes.
- `FRONTEND_URL`: no trailing slash. `https://webake-xxxx.vercel.app`, not
  `https://webake-xxxx.vercel.app/`.
- `ADMIN_PASSWORD`: Render stores it encrypted; it is only read by the seed
  script. You can delete this variable after seeding (optional hygiene).
- `BREVO_API_KEY`: the full `xkeysib-...` string.
- `SUPABASE_URL`: `https://xxx.supabase.co`, no trailing slash.
- `SUPABASE_SERVICE_ROLE_KEY`: the long JWT. Double-check it is the
  service_role key, not anon — uploads fail silently-ish (403 from Supabase)
  with the wrong one.

Everything else already has a value in `render.yaml` (`NODE_ENV=production`,
`BCRYPT_ROUNDS=12`, JWT lifetimes, sender name, business defaults).
`JWT_SECRET` is auto-generated by Render on first apply — you never see it,
which is the point. `PORT` is injected automatically and must NOT be set.

Click **Deploy** / **Apply**.

## Step 4 — Watch the first build

Open the service > **Logs**. You will see three phases:

1. **Build** (~2–4 min first time): `npm install && npm run migrate` in
   `backend/`. Dependencies first (`bcrypt`/`pdfkit` warnings are fine,
   errors are not), then the migrations. Expect:
   `[migrate] applying: 000_legacy_stash.sql ... applied` through
   `005_walkin.sql`, ending `done. 6 new migration(s) applied.`
   On later deploys this prints `skip (already applied)` for all six.
   (Migrations live in the build step because Render's free tier does not
   support pre-deploy commands — a failed migration fails the build, so a
   bad schema never goes live.)
2. **Start**: `node server.js` boots, then Render probes `GET /health`.
   `Live` status with a green dot means the health check passed.

Your API URL is shown at the top of the service page:
`https://webake-api-XXXX.onrender.com`. Copy it — Vercel needs it.

## Step 5 — Verify the API (before touching the frontend)

From any terminal, with `$API` = your Render URL:

```bash
# 1. Health + database connectivity
curl $API/health
# expect: {"status":"ok",...,"database":{"connected":true,...}}

# 2. Migrations actually ran (empty products table, not an error)
curl $API/api/products
# expect: {"success":true,"count":0,"products":[]}

# 3. Public settings (empty until seeded — must still be 200-shaped)
curl $API/api/settings/public
# expect: {"success":true,"settings":{...}}

# 4. Admin guard works (401, not 500)
curl -s -o /dev/null -w "%{http_code}\n" $API/api/admin/orders
# expect: 401
```

If all four pass, the backend is correctly deployed. The database is still
empty — that's step 6.

## Step 6 — Seed the database (once, via Shell)

1. Service page > **Shell** tab (opens a terminal inside the running service).
2. Run:
   ```bash
   cd backend && npm run seed
   ```
   (The shell starts at the repo root; the app lives in `backend/`.)
3. Expect: `admin created: crbwebake@gmail.com`, 8 products, 4 sample reviews,
   9 settings, `done.`
4. Re-run check (optional): run it again — every line should say "already
   exists" / "preserved". The seed never overwrites live data or the password.
5. Verify login works:
   ```bash
   curl -X POST $API/api/auth/admin/login \
     -H 'Content-Type: application/json' \
     -d '{"email":"crbwebake@gmail.com","password":"<ADMIN_PASSWORD>"}'
   ```
   Expect a JSON body with `token`. That token is the owner session — the
   admin panel stores it after sign-in.

## Step 7 — Point CORS at the real frontend (after Vercel deploys)

1. Service > **Environment**: find `FRONTEND_URL`, replace the placeholder
   with the exact Vercel URL (no trailing slash). **Save Changes.**
2. Render auto-redeploys (~1–2 min; code unchanged, only env differs).
3. Verify the browser origin is accepted:
   ```bash
   curl -H 'Origin: https://webake-xxxx.vercel.app' \
     -I $API/api/products | grep -i access-control-allow-origin
   # expect: access-control-allow-origin: https://webake-xxxx.vercel.app
   ```
   Then confirm a wrong origin is rejected (no header back):
   ```bash
   curl -H 'Origin: https://evil.example.com' \
     -I $API/api/products | grep -i access-control-allow-origin
   # expect: (no output)
   ```

## Step 8 — Day-two Blueprint behavior (what to expect)

- **Push to `main`** → Render auto-deploys: build → migrate (skips applied) →
  new code live. Zero action needed.
- **Edit `render.yaml`** (e.g. change plan/region/add a variable) → push →
  Render shows "Blueprint sync" and applies the diff, prompting for any new
  secrets. The file is the source of truth; dashboard edits to Blueprint-managed
  fields get overwritten on next sync (env VALUES you change in the dashboard
  are kept — only the key list syncs from the file).
- **Change an env value** (e.g. rotate a key) → Service > Environment > edit >
  Save → auto-redeploy. `JWT_SECRET`: use "Generate Value" again — all sessions
  die instantly, everyone signs in again.
- **Logs**: Service > Logs (live tail + history). Every 500 includes a stack in
  development only; in production you get the code + message, and email
  failures log with the order code for manual follow-up.
- **Shell**: one-off commands (`cd backend && node ...`). The filesystem is
  ephemeral — files you create there vanish on next deploy. Never store uploads
  on disk (the app doesn't; proofs go to Supabase).

## Troubleshooting

**Build fails on `bcrypt` / native modules.**
Render's Node 20 image builds bcrypt from source if no prebuild matches. This
needs no action — it just takes longer. If it truly errors, check the log for
a Node version mismatch (engines pin is `20.x` for exactly this reason).

**`[migrate] FAILED`.**
Read the first error line. Common causes: `DATABASE_URL` has a typo/trailing
space (connection refused), or you pasted the direct (5432) string and the
free-tier connection was refused — switch to the pooler (6543). Fix the env
var, Save (triggers redeploy), and migrate resumes: already-recorded files are
skipped, the failed file re-runs from scratch (each file is one transaction).

**Deploy succeeds but service stays `Deploying` / health check fails.**
`GET /health` must return 200 within the timeout. Causes: server crashed at
boot (read Logs top-down — a missing REQUIRED env var throws immediately with
its name), or the port binding failed (the app reads Render's injected `PORT`;
never set `PORT` yourself).

**`curl $API/health` shows `"connected":false`.**
The API boots without a database (health reports `degraded`, not a crash) so
you can diagnose. Check `DATABASE_URL` (pooler, correct password — the
password is the project's database password, not your Supabase login), and
confirm the Supabase project isn't paused (free projects pause after 7 idle
days; resume in the Supabase dashboard).

**First request takes ~50 seconds.**
Normal free-tier cold start after ~15 idle minutes. The frontend just waits;
subsequent requests are fast. Paid fix later: Render Starter (no cold starts).

**OTP endpoints return 503.**
`BREVO_API_KEY` empty or wrong — the mailer is disabled by design. Also
confirm the sender address was verified in Brevo (unverified senders get API
rejections, which surface as 500s on send, 503 only when the key is missing).

**Proof uploads fail.**
`SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` wrong, the `payment-proofs`
bucket missing, or you pasted the `anon` key instead of `service_role`.
The API logs the Supabase status code.

**Forgot `cd backend` in the Shell.**
`npm run seed` at the repo root fails (`missing script`) because the scripts
live in `backend/package.json`. Always `cd backend` first.

## Quick reference — all 17 env vars

| Key | Source | Change after deploy? |
|---|---|---|
| `NODE_ENV` | fixed `production` | never |
| `DATABASE_URL` | Supabase pooler | only if DB moves |
| `JWT_SECRET` | Render-generated | rotate if leaked (kills sessions) |
| `BCRYPT_ROUNDS` | fixed `12` | never |
| `MEMBER_JWT_EXPIRES_IN` | fixed `7d` | rare |
| `ADMIN_JWT_EXPIRES_IN` | fixed `12h` | rare |
| `FRONTEND_URL` | Vercel URL (step 7) | when frontend URL changes |
| `DEV_ORIGIN` | fixed empty | never in production |
| `ADMIN_EMAIL` | fixed owner email | never |
| `ADMIN_PASSWORD` | you invent | deletable after seeding |
| `BREVO_API_KEY` | Brevo dashboard | rotate per Brevo policy |
| `BREVO_SENDER_EMAIL` | fixed owner email | never |
| `BREVO_SENDER_NAME` | fixed brand string | rarely (rebrand) |
| `SUPABASE_URL` | Supabase API settings | only if project moves |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase API settings | rotate if leaked |
| `DEFAULT_LOW_STOCK_PIECES` | fixed `500` | prefer admin Settings page |
| `MIN_ORDER_BUNDLES` | fixed `300` | prefer admin Settings page |
